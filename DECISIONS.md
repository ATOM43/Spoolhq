# Decisions

Each entry is one decision and the reason for it. Add new entries at the bottom; to change one, add a new entry that supersedes it.

1. **Name: SpoolHQ** (Python package `spoolhq`, CLI `spool`). A spool feeds thread one turn at a time, as the loop feeds tickets; `spoolhq` was free as a package name and `spool` is short to type.
2. **UI: Tauri 2 + React + TypeScript.** Small native binaries on all three desktop platforms, with a mainstream, well-typed UI stack.
3. **Separate Python daemon (FastAPI).** Runs must survive closing the window, and the same daemon can run headless on a server.
4. **CLI: Typer.** Typed, minimal-boilerplate CLI that shares code and types with the daemon.
5. **Agent runtime: Claude Agent SDK behind an `AgentRunner` interface.** Use the best-supported coding agent now, without locking out other agents later.
6. **Storage: files for projects and tickets, SQLite for run history.** Specs and tickets stay readable and diffable in git; run history needs queries, not diffs.
7. **Stack templates: Copier.** It can both generate and later update projects from a template, which plain cookiecutter cannot.
8. **Only the planner, implementer and reviewer are LLM agents; everything else is plain code.** Gates, git, merging and tracker sync must be deterministic and testable.
9. **Local git first, GitHub optional.** The tool must work offline and without an account; GitHub adds pull requests on top.
10. **Licence: Apache-2.0.** Permissive, with an explicit patent grant, and compatible with the prior art we may borrow from.
11. **TypeScript pinned to 6.0.3, not 7.x.** typescript-eslint 8.71 supports TypeScript < 6.1; revisit when typescript-eslint supports 7.
12. **`.gitattributes` forces LF line endings.** Windows checkouts would otherwise get CRLF and fail the Prettier and ruff format checks.
13. **ruff's `S` (security) rules are on.** `shell=True` and similar unsafe calls are caught in CI rather than in review.
14. **`uv sync --locked` everywhere.** CI fails if `uv.lock` is out of date instead of silently re-resolving.
15. **The justfile's Windows shell is `powershell.exe`, not `pwsh`.** Windows PowerShell is always installed; PowerShell 7 is not.
16. **The GitHub repo is `ATOM43/spoolhq`.** It matches the package name, so there is one name to search for.
17. **The daemon binds to 127.0.0.1 only, with no override.** It runs agents on your code; nothing off the machine should reach it. A non-loopback `host` in config or env is a validation error.
18. **Local auth is a bearer token in `~/.spoolhq/token` (mode 0600, folder 0700).** Other local users and web pages cannot read it, and the CLI and desktop app need no login; it is compared with `secrets.compare_digest`.
19. **`GET /api/health` needs no token.** Clients use it to detect a running daemon, and it reveals nothing; every other `/api/*` route is protected by a middleware, so new routes are protected by default.
20. **Requests whose `Host` is not `127.0.0.1:<port>` or `localhost:<port>` get 400.** This blocks DNS-rebinding attacks from web pages, which send their own domain in `Host`.
21. **Logs are JSON lines from stdlib `logging` with a small formatter, no logging dependency.** One rotating file (10 MB × 5) that tools can parse; the token is redacted from every line as a backstop.
22. **Runtime dependencies are pinned exactly in `pyproject.toml`, like the dev tools.** SpoolHQ is an application, not a library; revisit if it is ever installed alongside other packages.
23. **The CLI's HTTP client ignores proxy environment variables (`trust_env=False`).** The daemon is always local; a user's `HTTP_PROXY` must not route CLI calls through a proxy.
24. **The daemon token stays in Rust.** The web view calls only the Rust commands `daemon_info` (port and whether a token exists) and `daemon_get` (status and body); Rust reads `~/.spoolhq/token` on each request and adds the `Authorization` header. Script in the web view can never read or leak the token, and the daemon needs no CORS.
25. **No HTTP plugin; the scope lives in the command.** `daemon_get` only builds `GET http://127.0.0.1:<port>/api/...` URLs from a character-checked path, and its client ignores proxy variables. The window's one capability grants just the two app commands (no `core:default`), via permissions generated from `build.rs`.
26. **Strict CSP.** Scripts, styles, fonts and images from `'self'` only, `connect-src` limited to Tauri IPC, `object-src`/`base-uri`/`form-action`/`frame-ancestors` `'none'`, plus `freezePrototype`. Tauri injects it into the built app; the Vite dev server in `pnpm tauri dev` is not covered.
27. **Settings uses the native `<dialog>`, not Radix Dialog.** Radix's scroll lock injects a `<style>` element, which `style-src 'self'` blocks; `<dialog>` traps focus and closes on Escape on its own.
28. **Fonts are bundled with `@fontsource`, no CDN.** Inter (400/500/600) and JetBrains Mono (400) ship as files (`assetsInlineLimit: 0`), so the app works offline, makes no third-party requests, and the CSP can stay `font-src 'self'`.
29. **shadcn/ui components use SpoolHQ's token names** (`bg-surface`, `text-ink-muted`, `bg-accent`, …) instead of shadcn's (`primary`, `muted`, `accent`), because shadcn's `accent` is a hover grey that clashes with our accent blue. They were copied from the new-york-v4 source and restyled.
30. **Status rules.** Health (no token) is checked before version, so a stopped daemon reads as "not running" even without a token file. A daemon that was reachable shows "Reconnecting…" for up to three failed checks (about 9 s), then "Daemon not running"; one that never answered is "not running" at once. Token, 401, 400 and other failures show a fourth state, "Daemon error", with the reason on Home.
31. **The app reads the port like the daemon:** `SPOOLHQ_PORT`, then `port` in `config.toml`, then 8765. Port and token are re-read on every check, so starting the daemon after the app needs no restart.
32. **Rust is pinned like the rest:** toolchain 1.99.1 in `rust-toolchain.toml`, crates with `=` versions, and `--locked` in the justfile. CI installs the toolchain with the runner's own rustup rather than a third-party action, and does not cache Rust builds yet.
33. **`@tanstack/react-query` is pinned to 5.104.3, not 5.104.4.** pnpm 12's minimum release age rejected the day-old 5.104.4; we pin an older release instead of exempting packages from the policy.
34. **Backend layering: `core` → `services` → `api`/`cli`, enforced by import-linter.** Routers and commands stay thin and call services; services never import FastAPI, Starlette, Typer or uvicorn, so the same logic serves HTTP, the CLI and tests; `core` (config, token, logging) depends on nothing above it. The contracts live in `daemon/pyproject.toml` and run in `just lint`, so a wrong import fails CI.
35. **Frontend: Feature-Sliced Design, enforced by lint.** `desktop/src/` is split into app, pages, widgets, features, entities and shared; slices expose an `index.ts`, import only from lower layers and never from a sibling slice. `eslint-plugin-boundaries` 7 checks this in `just lint`. We chose it over Steiger (the FSD project's own linter) because it runs inside ESLint, which we already run, and does not flag our deliberately empty placeholder slices.
36. **`core/logs.py` keeps its name** rather than becoming `core/logging.py`, so it never shadows the standard library's `logging` module.
37. **Design tokens live in `shared/styles/tokens.css`;** `app/styles/global.css` imports them with Tailwind, the fonts and the base layer.
38. **`unrs-resolver`'s install script is not run** (`allowBuilds` in `desktop/pnpm-workspace.yaml`). `eslint-import-resolver-typescript`, which lets the boundaries rules resolve `@/` imports, gets its native binary from an optional prebuilt package; the script is only a fallback.
39. **`project.yaml` is read and written with ruamel.yaml in round-trip mode.** It keeps the user's comments, key order and quoting when SpoolHQ later edits the file, and its loader never constructs Python objects from tags. Saving rewrites only values that changed and leaves out settings the user did not write.
40. **`spool init` builds the workspace in a temp folder next to the target and renames it into place.** A failure part-way leaves nothing behind, and an existing project folder is never touched. All inputs (name, repo, branch, remote) are checked before anything is created.
41. **Project names are slugs: `^[a-z0-9][a-z0-9-]{0,62}$`, checked with `fullmatch`.** The name is also the folder name, so it cannot contain `/`, `..` or anything else that escapes `projects_dir`, and it works as a branch or URL segment later. `project.yaml`'s `name` must match its folder.
42. **CLI commands for local file operations call services directly; the daemon is not needed.** `spool init` and `spool project validate` only read and write files in `projects_dir`; routes for projects come with T19 and will call the same service.
43. **`repo` in `project.yaml` must be an absolute path or start with `~`.** A relative path would depend on the directory `spool` runs from; `spool init` writes the resolved absolute path.
44. **85% line-coverage floor on the daemon, enforced in CI** (`--cov-fail-under=85` in `just test`), to be raised as the code grows. Only `if TYPE_CHECKING:` blocks are excluded; the desktop app reports coverage with no threshold yet.
45. **A ticket's body is kept as the exact original text and never re-rendered.** Users write notes, links and code in it, and agents edit it; a markdown re-renderer would reflow or "fix" text nobody asked it to touch. Only the frontmatter is parsed, and the Done-when checklist is read from the body without changing it.
46. **Saving a ticket rewrites only the frontmatter lines of keys that changed.** The lines of each key are found from ruamel.yaml's positions and replaced in the original text, keeping the key line's comment, the old quote style and list layout, and the file's line endings; the result is parsed again to check it. A whole-document ruamel dump keeps comments but not all spacing, so a status change would otherwise show up as noise in `git diff`. A frontmatter that cannot be updated line by line (one flow mapping) falls back to ruamel's full rendering.
47. **The editor for `spool tickets edit` runs as an argument list.** `$VISUAL` / `$EDITOR` is split with `shlex.split` (non-POSIX mode on Windows, so backslashes in paths survive), the program is resolved with `shutil.which`, and the file name is appended; no shell is involved, so the setting cannot chain commands. The fallback is `nano` on POSIX and `notepad` on Windows.
48. **Ticket frontmatter is validated in Pydantic's strict mode.** `phase: "1"` or `review_required: "yes"` are errors instead of being coerced, so what SpoolHQ reads is what the file says, and a save never changes a value's type.
49. **`spool tickets edit` keeps its backup as a hidden `tickets/.<file>.bak`** until the edit is valid or restored. It survives a crash next to the file it belongs to, and listing ignores hidden files.
50. **Round-trip fixtures are marked `-text` in `.gitattributes`** (and unset in `.editorconfig`), so git and editors keep their CRLF endings, missing final newlines and byte-order mark on every platform.
51. **`git.remote` follows GitHub's naming rules.** Owners are 1–39 letters, digits or hyphens; repositories are 1–100 letters, digits, `.`, `_` or `-`; neither may start with `-` or `.`, which also rules out `.` and `..` as repository names.
52. **The transition table in `services/scheduler/transitions.py` is the only source of truth for status changes.** `check_transition` reads it and nothing else hard-codes a move; `docs/scheduler.md` shows the same table and a test fails if the two differ. Moving to `running` additionally needs every dependency done.
53. **Setting the status a ticket already has is a no-op, not an error.** Retries and repeated clicks stay harmless, and `apply_transition` writes nothing, so the file and its modification time are untouched.
54. **Ties on the critical path go to the lower ticket ids, compared from the start of the chain, and hours are summed as decimals.** The same plan always shows the same path (T04 over T06 on the dashboard plan), and float rounding (`0.1 + 0.2`) never decides a tie.
55. **The scheduler refuses an invalid plan.** `next_ready`, `explain_idle`, `waiting_on` and the progress figures raise `PlanError` listing every `validate_plan` problem rather than guessing around a missing dependency, a cycle or a duplicate id. `spool plan next` and `spool plan summary` also refuse while any ticket file fails to load, and `apply_transition` refuses to start a ticket then, because a dependency could be hiding in the broken file. Other status changes don't consult the plan, so they still work.
56. **Cycles are found by a depth-first walk in id order, one cycle per back edge, each rotated to start at its lowest id.** Every set of tickets that depend on each other is reported, deterministically and in linear time, without enumerating every loop of a tangled group (which can grow exponentially).
57. **Arrows in plan output point in work order** (`T07 → T08`: T08 depends on T07), in cycles and in the critical path alike.
58. **CLI forces UTF-8 on stdout/stderr.** Messages keep their arrows (`blocked → done`, `T01 → T02 → T01`), but on Windows a redirected stream (`spool plan check > out.txt`) falls back to the console code page, such as cp1252, which cannot encode `→`, so the command crashed. The `spool` entry point (`cli.main:main`, also behind `python -m spoolhq`) reconfigures both streams to UTF-8 before Typer runs, keeping each stream's `errors` setting, so output is the same bytes on every OS. No ASCII fallback.
59. **Run history is stdlib `sqlite3` in WAL mode with `synchronous=NORMAL`, no ORM.** `<workspace>/.spoolhq/state.db`, one connection per `RunLog` behind a lock, `isolation_level=None` and an explicit `BEGIN IMMEDIATE` … `COMMIT` per operation. WAL with `NORMAL` keeps every committed transaction through a crash of the process (the case recovery handles), at a fraction of `FULL`'s fsync cost; a power loss or OS crash can drop the last few transactions, which only loses the newest history, never corrupts it. No new dependency.
60. **Schema migrations are an ordered list of SQL scripts tracked by `PRAGMA user_version`.** Opening a database runs the scripts it is missing, re-reading the version under the write lock so two processes never run the same script. A database newer than the code is refused (`upgrade SpoolHQ`) rather than read with the wrong assumptions; a file that isn't SQLite is refused as `not a SpoolHQ database`. Version 1 ships with T07.
61. **Events are append-only, enforced by triggers.** `BEFORE UPDATE` and `BEFORE DELETE` triggers on `events` raise `events are append-only`, so neither a bug nor a hand-run statement can rewrite history that the UI and later audits rely on.
62. **Attempt numbers count per ticket across all its runs, and each attempt has its own folder `runs/<ticket>/<NNN>/`.** `UNIQUE(ticket_id, number)` keeps them distinct, the folder path is stored in the row relative to the workspace, so every attempt's files are found from the database alone, and a ticket's folders sort in the order they ran. The ticket id is checked against the ticket id pattern before it is used in a path, and only four file names can be written.
63. **Cost is stored as integer micro-USD (`cost_micro_usd`).** Sums are exact (no float rounding across many small charges), and `NULL` means "no cost reported", which differs from a cost of 0 (a subscription backend may report none).
64. **The event bus is synchronous and bounded, with lag-and-resync instead of back-pressure.** Publishing never blocks the run loop: each subscriber has a bounded queue, and one that overflows is marked `lagged`, gets nothing more and catches up from the database with `events_since(last_id)`. The database, not the bus, is the source of truth, so a slow WebSocket client can always recover without the bus buffering without limit. Being synchronous and thread-safe, it bridges to asyncio (T19) with `call_soon_threadsafe` from an optional `notify` callback. A failing subscriber is logged and marked lagged; it never affects the publisher or others.
65. **Persist before publish.** Events reach the bus only after their transaction commits, in id order (published while the run log's lock is still held), and a failed transaction publishes nothing. A subscriber never sees an event the database doesn't have, so resyncing from `events_since` is always consistent with what it already received.
66. **Crash recovery is by daemon instance, made safe by a single-instance lock.** Each daemon start gets a `daemon_instance` (`uuid4().hex`) stored on the runs it starts; at startup, `running` and `paused` runs of any other instance are marked `interrupted`. That is only correct if no other daemon is alive, so `spool serve` first takes an OS lock on `~/.spoolhq/daemon.lock` (`fcntl.flock` / `msvcrt.locking`, stdlib only) with the pid written in the file, and a second daemon exits 1. The OS drops the lock when the process dies, so a crash leaves no stale lock to clean up. T02 had no such guard; the lock lives in `core/daemon_lock.py` because it is about the daemon process, not a domain. `awaiting_approval` runs are left alone: an approval waits on a person, not on the daemon.
67. **Recovery touches only the database.** Setting the interrupted ticket's file status back (`running` → `ready`) is left to the run loop (T13), which owns ticket status changes during a run, and removing leftover worktrees to T08, which owns worktrees. Recovery stays one small, testable transaction.
68. **`spool runs` reads `state.db` directly, read-only.** Like the other local commands (42), it calls the service without the daemon, opening the file with `mode=ro` and `query_only`, so a read never migrates, never runs recovery and never changes the file; a workspace without `state.db` simply has no runs.
69. **An empty attempt folder left by an attempt that never committed is reused.** `start_attempt` creates the folder inside its transaction (`exist_ok=False`) and removes it if the transaction fails, but a daemon killed between the two leaves an empty folder for a number the database never recorded; refusing it would block that ticket for good. Only an empty folder is reused; one with files raises `FileExistsError`.
70. **The daemon finds workspaces with `list_workspaces(projects_dir)`** (in `services/projects/`): folders with a slug name and a `project.yaml`, so staging folders from an interrupted `spool init` and stray files are skipped.
71. **One worktree per run, not per attempt.** Gate and review retries continue in the run's worktree, so the implementer fixes its own work with the failing output in front of it instead of redoing everything from a fresh checkout, and a ticket has at most one worktree at a time (`<root>/<project>/<ticket_id>`, refused a second time with `WorktreeExistsError`). The attempt files in `runs/<ticket>/<NNN>/` still record each attempt separately.
72. **SpoolHQ owns only the branches it marked.** Creating `feat/<id>-<slug>` also sets `git config branch.<branch>.spoolhq <run_id>` in the main repository; teardown, recovery and the stale-branch recreate delete only branches with that marker (and never the default branch), and `git branch -D` removes the marker with the branch's config section. A same-named branch without the marker is somebody's work and stops `create` with a message saying so. The marker lives in git's own config, so it survives a lost `state.db` and needs no extra file.
73. **A new worktree needs a strictly clean main repository, untracked files included.** `git status --porcelain=v1 -z --untracked-files=normal` must be empty (ignored files don't count), and no rebase, merge, cherry-pick or revert may be in progress. The worktree starts from the committed default branch either way, but an uncommitted change or a half-done merge in the main copy means a person is working there, and T14 will later merge into it; refusing up front is clearer than discovering it at merge time.
74. **SpoolHQ's own commits use `--no-verify`.** The gates are the checks, with timeouts and recorded output; repository hooks are code SpoolHQ doesn't control and can hang, prompt or rewrite files after the gates passed. Only `pre-commit` and `commit-msg` are skipped this way.
75. **No fetch or push until T17.** Worktrees start from the *local* default branch from `project.yaml`, so creating one needs no network or credentials and never moves the user's refs. Remotes, fetching and PRs arrive with T17.
76. **git 2.36 or newer.** `git worktree list --porcelain -z` (NUL-separated, so paths with newlines or spaces parse) first shipped in 2.36. The daemon checks `git --version` once at startup and logs an error for an older git instead of refusing to start, so the rest of the app stays usable.
77. **Startup recovery keeps the worktrees of blocked and awaiting-approval runs.** Their latest run waits on a person, who needs the work to inspect or approve; everything else under the project's root is removed. The rule is built in `api/` from the run log and passed to `recover_worktrees` as a `keep(ticket_id)` callable, so `services/git` imports no other service. If the run log can't be read, the worktree is kept.
78. **Ticket status reconciliation is still owed by T13.** Recovery removes worktrees and the run log marks runs `interrupted`, but neither changes a ticket file: putting a `running` ticket back to `ready` belongs to the run loop, which owns status changes during a run.
79. **The ticket id pattern moved to `core/ids.py`.** `services/git` needs it for branch names and paths but may not import `services/tickets` (which imports `services/projects`, which imports `services/git`); `services/tickets` and `services/runs` import it from there too, so there is still one pattern.
80. **The worktree root is a setting, `worktrees_dir`** (`SPOOLHQ_WORKTREES_DIR`), defaulting to `worktrees/` in the SpoolHQ home folder, like `projects_dir`. Tests get it inside their temp home for free.
81. **`run_git` also removes `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and the other repository-location variables, and gives git an empty stdin.** git sets them for hooks, so a daemon or test started from a hook would otherwise act on that repository instead of `cwd`; an empty stdin means no git command can ever wait on the daemon's terminal.
82. **Commits run with `user.useConfigOnly=true`.** Without a configured `user.name` / `user.email` git would otherwise guess `user@hostname` on some systems and commit under it; with it, git refuses and `commit_all` raises the documented message. Identities from `GIT_AUTHOR_*` variables still work.
83. **Only entries named like a ticket id, directly under `<root>/<project>/`, are SpoolHQ's.** Listing and recovery ignore anything else there (a `notes/` folder, nested worktrees) as well as every worktree outside the root, so recovery can only ever delete what `create` could have made. A registered worktree whose folder was deleted by hand is pruned and its marked branch left for the next `create` to recreate, so recovery never deletes a branch whose work it hasn't looked at in a worktree.
84. **SpoolHQ's git calls never run repository hooks.** `run_git` sets `-c core.hooksPath=<home>/hooks-disabled`, a folder that must stay empty (checked with `os.scandir` before every call; anything in it is an error and no git process starts). `--no-verify` alone skipped only `pre-commit` and `commit-msg`, so `post-checkout`, `prepare-commit-msg` and `post-commit` still ran, and a repository whose `core.hooksPath` is a tracked folder let the agent write a hook in its worktree that the daemon then ran outside the agent's permission policy. Commits keep `--no-verify` as a second guard. The folder is derived from the home folder (like `worktrees/`) rather than being its own setting, so it cannot be pointed at a folder that holds hooks.
85. **SpoolHQ's git calls never sign.** `run_git` sets `commit.gpgsign=false`, `tag.gpgsign=false` and `tag.forceSignAnnotated=false`, so a user's signing config cannot make SpoolHQ's commits and tags wait on a passphrase prompt or fail on a missing signing program. Signed commits may come back later as an explicit opt-in.
86. **A Graphify code graph is committed in `graphify-out/` for agent context.** Graphify 0.9.92 (`graphifyy` on PyPI, Apache-2.0), installed as a uv tool, not a project dependency. It is built offline from code only (`GRAPHIFY_BACKEND=none graphify extract . --code-only`, then `graphify cluster-only . --no-label`), so no source leaves the machine and no API key is needed; `graphify .` is the assistant-skill form of the same build. `GRAPH_REPORT.md`, `graph.json` and `graph.html` are committed; the cache, `manifest.json` and `.graphify_*` files are ignored (`.graphify_root` holds an absolute local path). The graph is refreshed by hand until T28 adds SpoolHQ's own Graphify support; Graphify's Claude Code hook and generated `CLAUDE.md` block are not installed.
87. **Daemon tests mirror the source layout.** `tests/core/`, `tests/api/`, `tests/cli/` and `tests/services/<domain>/`, with the folder name dropped from file names (`tests/cli/test_plan.py`). Every test folder, `tests/` included, is a package (empty `__init__.py`) so same-named files in different folders don't collide, under pytest's default `prepend` import mode; shared helpers are imported as `tests.conftest`. Fixtures used by one folder live in its `conftest.py` (only `wt_repo`, `wt_root` and `manager`, in `services/git/`); everything used by more than one folder, and the autouse `home`/`projects_dir`, stays in `tests/conftest.py`, which also exports `FIXTURES_DIR` for the shared `tests/fixtures/` data. Integration tests stay marker-based, not in a folder. `tests/test_layout.py` enforces the layout; `test_version.py` went to `core/` because it checks the package's own `__version__`, not the CLI.
88. **The agent policy is enforced by Claude Code, in four layers; SpoolHQ builds the configuration and verifies it took effect.** (1) `--restricted` confines the file tools to the worktree and ignores repository settings and hooks; (2) `--permission-mode dontAsk` with `--permission-prompts none` and an explicit allowlist; (3) the OS sandbox, with no network and the credential files denied; (4) a scrubbed environment. SpoolHQ never passes `--dangerously-skip-permissions` or `bypassPermissions`; a test fails if either string appears in `services/agents/` outside comments and docstrings. Writing our own enforcement (a path hook, a command parser) would be weaker than the OS sandbox and would have to track every Claude Code change.
89. **The allowlist is the project's stack commands plus read-only git, two rules per command.** Every command in `project.yaml`'s `commands` (`install`, `lint`, `test` and any others) and `git status`, `git diff`, `git log`, `git show` become `Bash(<cmd>)` (exact) and `Bash(<cmd> *)` (prefix). A stack command containing `; & | < > $ ` ( ) * ? [ ] { } \`, a newline, or leading or trailing spaces is refused with `PolicyError` naming the field, because it would widen the rules. The file tools `Read`, `Edit`, `Write`, `Glob` and `Grep` are allowed as a whole, since `--restricted` already confines them to the worktree.
90. **The OS sandbox is required.** The agent writes the tests that `just test` runs, so the allowlist alone is no boundary; the sandbox is. Native Windows, where Claude Code has no sandbox, is refused with a message pointing to WSL2; Linux without `bwrap` or `socat` is refused with an install hint (`sudo dnf install bubblewrap socat` on Fedora); `failIfUnavailable: true` makes Claude Code refuse rather than run unsandboxed, and `autoAllowBashIfSandboxed: false` stops it approving sandboxed commands that aren't on the allowlist.
91. **No network for the agent's commands in v1** (`allowedDomains: []`, `strictAllowlist: true`). Installs run in the gates, as code, outside the agent.
92. **Sandboxed commands may not read the usual credential files or the SpoolHQ home:** `~/.ssh`, `~/.aws`, `~/.config/gh`, `~/.gnupg`, `~/.netrc`, `~/.docker/config.json`, `~/.kube`, `~/.git-credentials`, `~/.config/git/credentials`, `~/.npmrc`, `~/.pypirc`, `~/.local/share/keyrings`, and the SpoolHQ home, which holds the API token. Worktrees live inside the home by default (`<home>/worktrees/…`), where denying the whole folder would deny the worktree itself; then the list has the token file plus every entry of the home except the folders on the way down to the worktree.
93. **The `claude` process gets only an allowlisted environment.** `PATH`, `HOME`, user, locale, temp, XDG, D-Bus, `CLAUDE_CONFIG_DIR` and proxy variables (and Windows' system variables), plus `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` and `DISABLE_AUTOUPDATER=1`. `ANTHROPIC_API_KEY` is passed only for API billing: with it in the environment Claude Code bills the API instead of the subscription. `detect()` therefore asks `claude auth status` without the key first, and offers it only when there is no subscription login, so a subscription always wins.
94. **The prompt goes on stdin, never as an argument.** It isn't visible in the process list, isn't limited by command-line length (Claude Code caps stdin at 10 MB; a larger prompt raises `ValueError`) and can never be read as a flag. Ticket and prompt text are untrusted and never reach argv or rules.
95. **A usage limit is an outcome, not a failure.** The runner returns `usage_limited` with `reset_at` (from a rejected `rate_limit_event`'s `rate_limit_info.resetsAt`, or the epoch after `usage limit…|` in the error, else `None`) and no error; T13 turns it into a paused run.
96. **Cost and tokens.** Subscription runs report tokens and `cost_micro_usd=None` (Claude Code's own estimate is ignored); API-key runs report `total_cost_usd` as integer micro-USD via `Decimal`, as the run log stores it (63). `input_tokens` counts uncached input, cache writes and cache reads, because with prompt caching uncached input is a handful of tokens per turn and a token budget on it alone would never trip; `Usage` events keep the breakdown, and assistant usage is counted once per message id.
97. **Claude Code 2.1.259 or newer.** `--permission-prompts` (needed so denials are final and reported) first shipped there; an older CLI is refused with `Claude Code 2.1.200 is too old; SpoolHQ needs 2.1.259 or newer (run: claude update)`.
98. **The adapter also accepts the `default` permission mode in `init`.** With `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`, Claude Code 2.1.302 prints `Permission mode forced to default — CLAUDE_CODE_SUBPROCESS_ENV_SCRUB is set` and reports `permissionMode: "default"`, whatever `--permission-mode`, `--allowedTools` or settings say (checked on 18 Oct 2026). Dropping the scrub would leave `ANTHROPIC_API_KEY` in the environment of every command an API-billed agent runs; keeping `dontAsk` strictly would stop every run. With `--permission-prompts none`, `default` denies everything that isn't pre-approved, as `dontAsk` does (the real run shows the python call denied and the allowlisted write allowed), so the adapter accepts `dontAsk` or `default` and stops on any other mode. The parser's own default stays `dontAsk` only, and the fake runner uses the adapter's set.
99. **The `init` message is checked before anything else is believed.** Any tool not requested (anything outside `--tools`, any `mcp__*`, `WebFetch`, `WebSearch`), an unexpected permission mode, or an assistant, user or result message before `init` raises `PolicyViolation`; the adapter stops the process and returns `error` with `policy not enforced: …`.
100. **`Glob` and `Grep` are in `--tools` and `--allowedTools`, and the settings include `disableAllHooks: true`.** Claude Code 2.1.302 accepts and reports both tools in a real run; `disableAllHooks` is a documented setting. It is redundant with `--restricted` (which already skips repository settings and their hooks) but costs nothing.
101. **`FileEdit` comes from a successful tool result, not the tool call.** An `Edit` or `Write` counts once its `tool_result` arrives without `is_error` and only if its path resolves inside the worktree; a denied or failed edit is not in `files_changed`, and one outside the worktree is logged as a warning.
102. **A worktree must not contain the user's home, the SpoolHQ home or a denied path, or sit inside one.** Sandboxed commands may write anywhere in the worktree, so such a worktree would let them write `~/.ssh/authorized_keys` or the token; `AgentPolicy.for_worktree` and `ClaudeCliRunner.run` refuse it with `PolicyError`.
103. **`ClaudeCliRunner`'s `platform` parameter only changes `detect()`'s sandbox rules.** The environment allowlist and process handling (process groups, signals) always follow the OS the daemon runs on, so tests can pretend to be Linux on the Windows runner and still start a working Python.
104. **SpoolHQ cleans up after Claude Code's env scrub.** With `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`, Claude Code 2.1.302 creates 19 empty placeholders in its working folder (`.env*`, `package.json`, lockfiles, `.npmrc`, `.claude/agents/`, `node_modules/.bin/`, …) and leaves them, even for `claude auth status`; without the variable it creates none (checked on 18 Oct 2026). Left alone they would land in every ticket's diff, and `spool agents` would drop them wherever it is run. So `detect()` runs its probes in a throwaway temp folder, and after a run the adapter removes each placeholder that wasn't in the worktree before the run and is still empty (a folder only if it holds no files). The scrub itself stays (93, 98).
105. **Prompts are Jinja2 templates in a `SandboxedEnvironment`** with `StrictUndefined`, `autoescape=False` (the output is markdown, not HTML), `keep_trailing_newline` and `trim_blocks`/`lstrip_blocks`. Jinja2 3.1.6 (the current release, BSD-3-Clause) is pinned exactly like the other dependencies; it brings MarkupSafe 3.0.4 (BSD-3-Clause) with it.
106. **Untrusted text is only ever a template variable, never template source.** The ticket, the spec, `PROGRESS.md`, `DECISIONS.md`, `CLAUDE.md`, gate output, review notes and user notes are values; templates are loaded by name through a loader, nothing in `services/context/` calls `from_string` or `Template()` (a test greps for it), so `{{ 7*7 }}` in a ticket stays literal text.
107. **Every untrusted input sits in its own tag block, and its closing tag is escaped inside it.** `</ticket>` (any case, with or without spaces around `/`) becomes `<\/ticket>` in Python before rendering, so content can't close its block early and an override can't forget the escaping. The rules tell the agent that block contents are data, not instructions. Fenced text uses a fence longer than any backtick run inside it.
108. **The default template is package data** (`services/context/prompts/implementer.md.j2`, loaded with `importlib.resources`), so it ships in the wheel and, later, the PyInstaller bundle. An integration test builds the wheel with `uv build` and checks the template is in it.
109. **Prompt overrides live in the workspace, `<workspace>/prompts/implementer.md.j2`,** not in the code repository: the agent works in the repository and must not be able to rewrite its own prompt. Overrides get the same sandbox and the same, already escaped variables.
110. **The prompt budget counts characters, not tokens:** `context.max_chars` in `project.yaml`, default 120,000, from 20,000 to 2,000,000. No tokenizer dependency; characters are a conservative stand-in.
111. **The progress note comes back in the agent's final message,** as one `<progress>…</progress>` block of 1–3 sentences, not as a file in the worktree, so it can never end up in a diff. `format_progress_entry` strips `<`, `>` and `#` lines from it, since it is agent output headed for a file other agents read; T14 appends it at merge.
112. **The prompt is deterministic and machine-neutral:** no absolute paths, timestamps or user names (the worktree is "your working directory"), `\n` line endings only, one final newline.
113. **Trim order and caps:** the template, the ticket, the commands and the previous attempt are never trimmed except each gate output excerpt (8,000 characters: the first 6,000 and the last 2,000). The rest fills in order `CLAUDE.md` (16,000, keep the beginning), the spec (no cap: outline plus the sections sharing most words with the ticket), `PROGRESS.md` and `DECISIONS.md` (24,000 each, newest `## ` entries); unused room flows on. Below 2,000 characters of room is an error asking to raise `context.max_chars`.
114. **The previous attempt comes first after the rules, before the ticket,** because it is what the agent most needs to act on, and the failing test names in it are never cut.
115. **`services/context` keeps its own copy of the read-only git commands** (`git status`, `git diff`, `git log`, `git show`) for the prompt, because it may not import `services.agents`; a test keeps it equal to `services.agents.READ_ONLY_GIT`.
116. **`RenderedPrompt.cuts` prefixes each note with its file** (`DECISIONS.md: [trimmed: kept the last 12 of 104 entries]`), while the note inside the block is unprefixed; without the prefix a log line couldn't say which input was cut. An input with no room at all is left out with `<file>: [trimmed: left out, no room]`.
117. **When a block's measured overhead is a few characters off after a cut** (fences drop leading and trailing blank lines), the renderer shrinks that block's room by the overshoot and tries again, up to three times; the final length is still checked against `max_chars`.
118. **Supersedes 5: agents run through the Claude Code CLI (see 88),** not the Claude Agent SDK. The `AgentRunner` interface stays, so other agents can still be added.
119. **Supersedes the keep rule of 77: startup recovery also keeps the worktrees of interrupted runs.** Recovery in the run log first marks every run a stopped daemon left `running` or `paused` as `interrupted`; until now the worktree recovery then removed those worktrees and branches, losing the agent's commits from a crash, reboot or restart. The run loop (T13) needs them to resume. `done` and `cancelled` runs, and tickets with no run, are still cleaned up.
120. **Claude Code's own files are denied to sandboxed commands:** `~/.claude` and `~/.claude.json` join the credential list (92), and the `CLAUDE_CONFIG_DIR` folder is added when that variable is set in the environment passed to `claude`. They hold Claude Code's login and session history. Only the agent's commands are denied; Claude Code itself still reads them. The adapter adds the `CLAUDE_CONFIG_DIR` folder to the policy before the worktree check, so a worktree inside it is refused like one inside any other denied path (102).
121. **`default_branch` must be a branch name, not any revision.** It is checked with `git check-ref-format --branch` and then `git show-ref --verify --quiet refs/heads/<name>`; `main~1`, `main^` or `main@{0}` used to pass the existence check, though worktrees branch from and later merge into a branch, not a revision. `show-ref` exit 1 means the branch doesn't exist; any other failure (a corrupt `packed-refs`) is reported as the git error.
122. **Each workspace's event bus starts at the database's last event id.** A fresh bus started at 0, so after a restart a subscriber that lagged before the first new event resynced with `events_since(0)` and got the whole history again.
123. **`RunResult.summary` keeps the end of the agent's final message,** the last 4,000 characters after a `[… N characters cut …]` line, instead of the beginning: the `<progress>` block the context package reads is at the end (111).
124. **The `claude` environment also passes the lower-case proxy variables, `NODE_EXTRA_CA_CERTS` and `SSL_CERT_FILE`** (extends 93). Behind a corporate proxy with its own CA, Claude Code could not reach the API without them; none of them is a secret.
125. **`spool serve` has no `--port` option;** the port comes from `SPOOLHQ_PORT` or `config.toml`. The CLI client reads the port from the settings, so a daemon started on another port with the flag was one `spool` couldn't reach.
126. **Shared helpers have one copy:** `check_ticket_id` and `id_key` in `core/ids.py`, `READ_ONLY_GIT` in `core/agent_policy.py` (replacing the copy and equality test of 115), the YAML setup and `to_plain` in `services/projects/yaml_io.py` (the tickets version, which also turns ruamel's scalar subclasses into plain values), and `hours` in `cli/common.py`. The ticket model's `id` validator keeps its own regex check, because its message (`id: must be T followed by 2 or 3 digits, like T04`) differs from `check_ticket_id`'s and is part of the validation output.
127. **No source file over 500 lines.** `just lint` runs `scripts/check_line_limit.py` (standard library only) over `daemon/src/spoolhq/**/*.py` and `desktop/src/**/*.{ts,tsx}`; tests (`daemon/tests/`, and `*.test.*` / `*.spec.*` next to the desktop code) are exempt. Exceptions go in its `ALLOWED` table with a reason; it is empty. Two files were over: `services/agents/claude_cli.py` (674) lost the command line, settings, environment, stub clean-up and worktree check to `claude_config.py`, keeping detection and process handling; `services/runs/log.py` (533) lost the column lists, row conversion, `fetch_run` and payload encoding to `rows.py`, keeping `RunLog` and its transaction. Package exports are unchanged; the config tests moved with their code to `test_claude_config.py`.
128. **Gates never use a shell.** A `commands.*` string is split with `shlex.split` (POSIX mode) and run as an argument list; the program is resolved with `shutil.which` on the gate's scrubbed `PATH`. `&&`, `||`, `|`, `;`, `>`, `<`, `` ` `` and `$(` are refused when `project.yaml` is validated (`project.yaml: commands.test: shell syntax isn't supported; put it in a justfile recipe`), and again before a gate runs; an unclosed quote is refused too (`can't be split into arguments: …`). A missing program is the `error` status with `gate 'test': program 'just' not found on PATH`. Nothing is expanded, so `$HOME` or `*.py` reach the program literally.
129. **Gates get a scrubbed environment:** the agent's allowlist (93, 124), moved to `core/agent_policy.py` as `allowed_env` so `services/gates` can use it without importing `services/agents`; minus `ANTHROPIC_API_KEY` and anything matching `*_TOKEN`, `*_KEY`, `*_SECRET` or `*_PASSWORD` (checked even though the allowlist has none today, so a future addition can't leak one); plus `CI=1`, `NO_COLOR=1`, `FORCE_COLOR=0`, `PY_COLORS=0` and `TZ=UTC`. Stdin is `DEVNULL`; stdout and stderr are merged.
130. **Known gap: gates have no filesystem isolation yet.** They run agent-written code with the user's own file access. The agent's commands are sandboxed (90); the gates' aren't. A later ticket will sandbox them; `docs/gates.md` says so.
131. **Install → lint → test.** If install doesn't pass (failed, timed out, couldn't start), lint and test are `skipped`; lint and test both run even if lint fails, so one retry sees every error.
132. **Timeouts and stopping.** `gates.timeouts` in `project.yaml` (whole seconds, 10–7,200; defaults install 600, lint 300, test 900; the defaults live once, in `services/gates`). On timeout the whole tree is stopped: on POSIX the command starts in a new session and the group gets SIGTERM, then SIGKILL after 5 s; on Windows `taskkill /T /F /PID <pid>` as an argument list. On POSIX the group is also SIGKILLed after a normal exit, so a server a test left running doesn't hold the pipe (or linger); if something outside the group still holds the pipe at the deadline, the gate is `timed_out`.
133. **Output is cleaned and capped while it streams.** Bytes are decoded as UTF-8 with `errors="replace"` (incrementally, so a character split across reads survives), ANSI escapes (CSI, OSC, charset selection, two-character) are stripped and `\r\n` becomes `\n`. The log holds at most 20 MB (whole lines; the line that would go over is replaced by `[output cut at 20 MB]`) and the process is drained to the end; `output_lines` counts every line printed. The excerpt and failing tests are computed from the log, so when it was cut they come from its first 20 MB. Passing gates get an empty excerpt and no failing tests.
134. **The excerpt keeps the first failure:** at most 8,000 characters: the first 20 lines, the 30 lines before the first failure line, that line and as many after it as fit, and the last 40 lines, in order, non-overlapping, with `[… N lines cut …]` between parts; output that fits is unchanged. Each part has a character budget (head 1,200, before 1,500, the failure line 1,000, tail 3,000, after: the rest; without a failure the tail gets the rest), so huge lines can't push the failure out, and a single line over its part's budget keeps its start and ends in `…`.
135. **The first failure line** is the first line of the strongest kind present (case-sensitive): pytest `FAILED `/`ERROR ` at line start; `Traceback (most recent call last)`; Vitest/Jest `FAIL ` at line start or a line starting with `×`/`✗`; `error[`, ` error TS`, `: error:`; then `error:` anywhere. For the Vitest/Jest kind leading spaces are allowed, because both tools indent those lines (` FAIL  src/a.test.ts > adds`); the pytest kind must start in column 0, where the short summary puts it.
136. **Failing test names are extracted deterministically,** in output order and deduplicated: pytest `FAILED`/`ERROR <node id>` lines (the id up to ` - ` or the end of the line, so a parametrize id containing ` - ` is cut there) and Vitest `FAIL <file> > <test name>` lines; nothing for other tools. They feed `failing_tests` in T10's `PreviousAttempt`.
137. **"Done when" items run nothing.** An item with a backticked command followed by `passes` gets that gate's result only if the backticked text exactly equals a configured command; anything else is `not_a_gate`, left to the reviewer, and never run, because ticket text is untrusted.
138. **`services/gates` returns T10-shaped plain data instead of importing `services/context`.** `GateRun.to_gate_failures()` gives the failed and timed-out gates as `GateFailureData` dicts whose keys are `GateFailure`'s fields (`command`, `exit_code`, `timed_out`, `output_excerpt`), so T13 can call `GateFailure(**data)`. `GateRun.passed` and `first_failure` (the first gate that failed, timed out or errored) are computed from the results. Two runs on the same worktree are equal apart from `duration_s`.
139. **The reviewer gets a fresh context, enforced by types.** `ReviewInputs` has no field for the implementer's transcript, its summary or its progress note, so they can't be passed in; each review attempt is a new `claude` process with no session reuse. The reviewer judges the code, not the implementer's description of it.
140. **The reviewer's tools are read-only.** `AgentPolicy.read_only` (default `False`) and `AgentPolicy.read_only_for(worktree, home)`: no stack commands, no git commands, the same deny list. The adapter passes `--tools Read,Glob,Grep` and `--allowedTools Read Glob Grep`, with no `Bash(…)` rules, `Edit` or `Write`; `--restricted`, `dontAsk`, the sandbox settings and the environment scrub are unchanged, and the writing policy's command line is untouched. For a read-only policy the `init` check requires exactly that tool set: an extra tool is a violation as before, and so is a missing one (`ClaudeStreamParser(exact_tools=True)`). Claude Code 2.1.302 reported exactly `Glob`, `Grep`, `Read` in the real runs.
141. **The verdict comes back as a `<verdict>{…}</verdict>` block at the end of the final message; the last block wins, and JSON in a code fence inside it is accepted.** Claude Code 2.1.302 has a `--json-schema <schema>` option for structured output in print mode (checked with `claude --help` on 18 Oct 2026); SpoolHQ doesn't use it, so any text-writing backend works and SpoolHQ always validates the JSON itself. The text is taken from the `result` message's full `result` field, because `RunResult.summary` keeps only the last 4,000 characters (123) and N reasons of up to 1,000 characters can be longer.
142. **The verdict schema is strict.** Pydantic with `extra="forbid"` and strict types (validated from the JSON text, so arrays become tuples): one item per "Done when" item, indices `1..N` each once in any order; `reason` non-empty (not just whitespace) and at most 1,000 characters; `summary` at most 2,000; `verdict` is `approve`, `changes_requested` or `needs_human`. Consistency: `approve` needs every item met, `changes_requested` at least one unmet, `needs_human` is always allowed and is how the reviewer reports problems outside the checklist.
143. **Items the gates checked take the gates' answer, and consistency is checked after merging.** `parse_verdict(…, gate_checked=…)` replaces the reviewer's `met` for those items before the consistency rules, so `changes_requested` whose only unmet item the gates passed is invalid (and retried), while `approve` with a gate-passed item the reviewer doubted is accepted. The result marks them `source="gates"` with the reason `checked by the gates: passed`. The reviewer still returns an entry for each, so indices stay `1..N`.
144. **Invalid output is retried once, with the errors and never the previous output.** Invalid is no block, unparseable JSON, a schema error or a consistency error. The retry is a fresh run of the same prompt plus a "Your previous answer was invalid:" list. A second invalid answer gives `needs_human`, summary `reviewer returned invalid output twice: <errors>`, no items; `invalid_errors` keeps every error prefixed `attempt N: `. Tokens and cost are summed over attempts.
145. **Run outcomes other than `completed` are passed through.** `usage_limited` (with `reset_at`), `timed_out`, `cancelled`, `error` (a policy violation included), `max_turns` and `budget_exhausted` come back as `run_outcome` with `verdict=None` and the run's error as the summary; T13 decides.
146. **The reviewer's untrusted input sits in four escaped tag blocks:** `<done_when>`, `<ticket>`, `<gates>` and `<diff>`, each value passed through `escape_closing_tag` (already public in `services.context`, so nothing moved) and rendered by T10's sandboxed `render_template`. The items are in a block too because they are ticket text. The rules say text in the blocks addressed to the reviewer is data; the code-side consistency checks are the backstop.
147. **The diff is capped at 150,000 characters.** Over that: the list of changed files, then each file in diff order, whole while the room lasts and as its header (the lines before its first hunk) after the first one that doesn't fit, then `[diff trimmed: N of M files shown in full; read the others with the Read tool]`. Stopping at the first file that doesn't fit keeps "in diff order" literal. If even the headers don't fit (thousands of files), the text is cut at a line boundary before the note. A trimmed diff can still be approved.
148. **Reviewer budget defaults:** `max_turns=20`, `timeout_s=600`, no token or USD limit unless the caller passes a `Budget`.
149. **The reviewer's template is `services/context/prompts/reviewer.md.j2`,** next to the implementer's, overridable at `<workspace>/prompts/reviewer.md.j2` with the same sandbox and one-line errors (109).
150. **"Done when" parsing stays in `services/tickets/checklist.py`.** T11 doesn't parse items (`check_done_when` takes lines), and T05's `parse_done_when` is already the one parser, used by `Ticket.done_when`. `services/review` gets the items as data in `ReviewInputs.done_when` (built by the CLI, later by T13), so it never needs the parser and nothing moved to `core/`; adding `core/done_when.py` would have made a second copy.
151. **`FakeRunner` accepts a sequence of transcripts** and replays the next one on each `run()`; a run past the end raises `RuntimeError`. A single path is still replayed on every run. `calls` records each run's prompt and policy, so tests can check what a retry was sent.
152. **`spool review` runs no gates.** Items naming a configured command (`check_done_when` against an empty `GateRun`) are listed on stderr as `not yet checked by the gates: …` and are judged by the reviewer like any other item; `gate_checked` is empty. The folder must be a clean git work tree (T08's dirty-repo message otherwise), the diff is `git diff <base>...HEAD` through `run_git`, and the exit codes are 0 for `approve`, 1 for `changes_requested`, `needs_human` and errors, 2 for any other run outcome.
153. **Note for T13:** commit the implementer's work before calling `review()` (only committed work is reviewed), and after the review run check that the worktree's `HEAD` and `git status` are unchanged; the reviewer is read-only, but this is the cheap check that it stayed that way.
154. **The daemon owns the run loop.** A run executes in a worker thread inside the daemon (`services/runloop/`, `app.state.runloop`), so it survives the terminal closing and can be paused, resumed or cancelled from another terminal. The CLI calls a small set of endpoints (`POST /api/projects/{name}/runs`, `…/runs/{id}/pause|resume|cancel`, `…/tickets/{id}/discard`, `GET …/runs/current`); the full REST and WebSocket API is T19. Requests from other threads only set flags (`cancel`, `pause`, `stop`) that the worker checks between steps; `cancel` is also the agent's cancel event.
155. **One run per project**, enforced by the loop's record of active runs (which names the ticket and run, and covers a paused run with no thread) plus `<workspace>/.spoolhq/run.lock`, taken by the worker with T07's lock code, now `core/daemon_lock.acquire_lock` (`acquire_daemon_lock` uses it; `LockHeld` is the base of `DaemonAlreadyRunning`). A second start fails with `a run is already active in 'demo' (T04, run 12)`, or `(pid 4242)` when another process holds the file. Same-status moves are no-ops in T06's table, so the lock, not the table, prevents a double start.
156. **One worktree per run; retries are new attempts in the same worktree**, so the agent builds on its earlier work.
157. **SpoolHQ commits, not the agent.** After each implementer attempt the loop commits everything in the worktree on the run's branch (`spool: T04 attempt 2`, T08's `commit_all`: no hooks, no signing). The reviewer reviews `git diff <base>...HEAD`; the worktree's `HEAD` and `git status --porcelain -z` must be the same after the review run, else the run is blocked with `reviewer changed the worktree`. An implementer that stopped early (`timed_out`, `max_turns`, `budget_exhausted`) is committed too, so the retry continues from its work.
158. **Files changed come from git** (`git diff --name-only <before> <after>` around the commit), not from the agent's file-edit events, so files written by commands count.
159. **The state machine** is the one in the ticket: pick → implement → commit → gates → review → integrate, as plain functions over a `RunContext` (`machine.py`). Gate failure → `gate_retry` while `limits.gate_retries` lasts, else blocked `gates failed after 3 retries: <first failing command>`; `changes_requested` → `review_retry` while `limits.review_retries` lasts, else `changes requested after 2 retries`; `needs_human` → blocked at once. A gate retry resets nothing: each counter counts its own rounds.
160. **Retry counters are read from the attempt rows, not kept in memory**: the number of the run's `gate_retry` / `review_retry` attempts that aren't `interrupted`. A resumed run (after a pause, a usage limit or a crash) therefore counts exactly like one that never stopped, and a cut-off attempt never counts.
161. **The retry prompt's previous attempt is read from the last finished attempt's files** (`gates.json`: failing tests and the `GateFailure` data; `review.json`: the unmet items with their reasons), so a resumed run builds the same prompt as an uninterrupted one. An early stop writes `{"stopped": "<outcome>"}` there, which becomes a short note in the prompt (under the template's "Note from the user" heading, the only free-text slot T10 has).
162. **Integration is a seam.** `Integrator.integrate(ctx) -> IntegrationResult` with `merged`, `conflict`, `failed` or `held` (a fourth status, so the default can say "not merged yet" without pretending to fail). `merged` → ticket and run `done`, worktree removed; `conflict` / `failed` → blocked with the message; `held` → `awaiting_approval`, worktree kept. The default `HoldForIntegration` holds every approved run (`T04 approved; merging arrives in T14 — worktree kept at <path>`); T14 provides the real one. Tests use a fake that returns `merged` and marks the ticket done.
163. **Every step is recorded in the run log**: attempt rows with kind and number, a new event kind `run.phase` per phase change whose `text` is the line `spool run` prints (`T04 attempt 2 · gates · ✗ test (2 failing)`), the implementer's and reviewer's raw streams in `transcript.jsonl`, `gates.json` and the gate logs, `diff.patch` and `review.json` in the attempt folder, and token usage per attempt (summed per run by `run_usage`). Individual agent events are not copied into the event table; the transcript has them.
164. **Run log schema version 2** adds `runs.progress_note` and `runs.reset_at`. `set_run_status(…, reset_at=)` stores a paused run's reset time and clears it on any other change; `set_progress_note` stores the implementer's note, extracted from the full final `result` text (not the 4,000-character summary) of its last completed attempt, for T14.
165. **Usage limits pause, never block.** `usage_limited` from either agent → the attempt `interrupted`, the run `paused` with `reset_at`, the ticket stays `running`, the worktree is kept. `ResumeTimer` resumes it at `reset_at` + 60 s: it polls the loop's injected clock once a second on its own daemon thread (so tests advance a fake clock and call `check()`), and is cancelled on shutdown. Without a known `reset_at` the run waits for `spool run resume`. Resume starts a new attempt of the same kind.
166. **Other agent outcomes:** `timed_out`, `max_turns` and `budget_exhausted` are a failed attempt of the current phase and use up a retry: the implementer's a gate retry (the work is committed first), the reviewer's a review retry. `error`, a policy violation included, blocks at once with the error text and is never retried.
167. **Budget per ticket** (`agents.budget_per_ticket`) is checked before each attempt against the run's total usage: `budget used up: 2,104,331 of 2,000,000 tokens` or `budget used up: $2.10 of $2.00`. The implementer also gets the tokens left as its `max_tokens`, so an attempt can't overshoot by much. The implementer's other limits are fixed for now: 100 turns, 30 minutes.
168. **Cancel** stops the current agent (T09's cancel event), removes the worktree and its branch (T08 teardown, marked branches only), marks the run `cancelled` and puts the ticket back to `ready`. **Pause** waits for the current agent call to finish (its work is committed), then stops before the next step; the attempt it cut off is `interrupted`, so resume runs a new attempt of the same kind, which doesn't count. A paused run is still the project's active run; cancelling it cleans up at once.
169. **Crash recovery:** an interrupted run's ticket stays `running`; nothing resumes automatically. `spool run resume` reopens the newest interrupted run whose ticket is still running (`RunLog.reopen_run`, the one way out of a terminal status: back to `running` under the current daemon instance) and continues in its kept worktree with a new attempt of the interrupted kind (`next_kind`: an interrupted attempt repeats, `gates_failed` → `gate_retry`, `changes_requested` → `review_retry`, an approved one only integrates). A missing worktree blocks the run with a hint to discard. `spool run discard <ticket>` tears down the worktree and branch and puts an interrupted (`running`) or `blocked` ticket back to `ready`.
170. **Daemon shutdown leaves runs for recovery.** The lifespan closes the loop: the timer stops, running agents get `stop` and `cancel`, and the loop waits up to 20 s for the workers. A worker that sees `stop` marks its attempt `interrupted` and leaves the run `running`, so the next startup marks it `interrupted` and keeps the worktree instead of tearing it down as a cancel would.
171. **`run all`** loops `next_ready()` in the same worker until no ticket is ready or a run doesn't end `done` (blocked, paused, cancelled, or held for integration). With the default integrator it stops after the first approval until T14 lands.
172. **Init permission mode `default` is accepted only when it is really safe** (T09 follow-up): `permission_modes(env, argv)` allows it only when `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` is in the environment actually passed to `claude` and `--permission-prompts none` is on its command line; otherwise only `dontAsk`. `FakeRunner` checks with the environment and flag the adapter always passes.
173. **Event bus listeners stay cheap:** the loop does no work in a bus callback, and the resume timer only starts a worker thread.
174. **`spool run` takes the project as its first argument** (`spool run next <project> [<ticket>]`), like every other `spool` command, rather than the ticket's `spool run next [<ticket>]`, since the daemon serves several projects. `pause`, `resume` and `cancel` take `--run <id>`, defaulting to the project's current (else latest) run. `next`, `all` and `resume` follow the run by polling `runs/current` once a second and printing each new phase line (event ids only grow, so `run all` switching runs needs no special case), exit 1 if the run ended `blocked` or `cancelled`, and Ctrl-C detaches with `run continues in the daemon; spool run status to check`.
175. **The run endpoints live in `api/routers/runs.py`** (models in `api/schemas/runs.py`), following the codebase's one-router-per-resource layout rather than the ticket's `api/runs.py`. Unknown project, run or ticket → 404; any other refusal → 409; the message is in `detail`, which the CLI's client now prints for 404/409 answers (`ApiClient.post` added).
176. **A project created after the daemon started gets its run log on first use** (`RunRegistry.open(workspace)`, which also runs recovery for it), so `spool init` doesn't need a daemon restart before `spool run`.
177. **The default branch is only ever fast-forwarded; nothing is rebased or merged on it.** All history work happens in the run's worktree. `git merge --no-ff --no-commit <default_branch>` brings the current main in, replacing the plan's "rebase onto main": the result is squashed into one commit, so merge and rebase give the same tree, and a merge leaves the worktree, never main, in a conflicted state. The user's main checkout only ever sees `merge --ff-only`, `update-ref` and `git tag`. SpoolHQ never rebases, resets, stashes, checks out or cleans there.
178. **Advancing main is a compare-and-swap.** With the default branch checked out in the main checkout: it must be clean (T08's `ensure_clean`) with `HEAD == main_sha`, then `git merge --ff-only <commit>`. Otherwise: `git update-ref refs/heads/<default> <commit> <main_sha>`, which fails if main moved. If main moved since the merge-in, integration starts over at the merge-in, at most 3 tries in all, then the run is blocked: `main kept moving during integration`.
179. **A dirty main checkout never blocks the ticket; integration waits.** The ticket and run stay `awaiting_approval` with `main checkout has uncommitted changes in <repo>; commit or stash them, then run spool run integrate <project> <ticket>`, checked before the merge-in and again at the advance. A rebase or merge in progress there waits the same way. A main checkout with another branch checked out isn't checked at all, since `update-ref` doesn't touch its files.
180. **Conflicts go back to the implementer once.** A conflicting merge-in leaves the worktree mid-merge and starts a `conflict_retry` attempt whose prompt lists the files (T10's `conflict_files`, read live from the worktree, so a resumed attempt gets the same list). After it, SpoolHQ stages everything and requires `git ls-files -u` to be empty and no conflicting file to have a marker line (`=======`, or `<<<<<<<` / `>>>>>>>` followed by a space or the end of the line). Then it concludes the merge, and the gates and the reviewer run as usual. Markers left behind, or a second conflict in the same run, block with `merge conflict with main in: <files>`. The check also runs after a conflict retry that stopped early (turn limit, timeout), because committing would conclude the merge with the markers in it.
181. **The gates rerun only when the merge-in brought something, with T13's gate-retry rules.** If main had nothing new, the approved attempt's gates already ran on that exact tree. A failure on the merged code is a `gate_retry` (new `IntegrationStatus.GATES_FAILED`). Its results and logs replace the approved attempt's `gates.json` and gate logs, because the retry prompt reads the last finished attempt's files; the earlier pass is still in the run's phase lines. After the merge-in the worktree's `base_sha` becomes `main_sha`, so the reviewer's diff no longer includes main's own changes.
182. **The squash commit is built on a detached `HEAD` in the worktree.** `git switch --detach`, `git reset --soft <main_sha>`, the diff guard, the `PROGRESS.md` entry, commit. Its only parent is `main_sha`. The run branch never moves, so restoring the worktree after a block, a moved main or a crash is `git checkout --force <branch>` there (plus `git merge --abort` if a merge is open). `git reset --soft` refuses to run mid-merge anyway, so the merge is always concluded first.
183. **Commit message.** `T04: <title>`, a blank line, the run's progress note wrapped at 72, a blank line, then `SpoolHQ-Ticket: T04` and `SpoolHQ-Run: 12`, passed as one argument. Whitespace and control characters in the untrusted title become single spaces, and the whole subject line (`T04: ` included) is cut to 72 characters. No note, no body paragraph. Author and committer come from the user's git config with `user.useConfigOnly=true`, as in T08.
184. **`PROGRESS.md` is updated in the squash commit.** T10's `format_progress_entry` is appended with the merge date in UTC. A missing file is created with a `# Progress` heading first. The file is edited as bytes, so its existing line endings and encoding are kept.
185. **Each merged ticket gets a lightweight tag `ticket/<id>`.** Signing is already off for SpoolHQ's git calls. An existing tag blocks the run before anything else, so before main moves: `tag ticket/T04 already exists; delete it or rename the ticket`.
186. **The diff guard runs on the staged squash (`git diff --cached --name-only <main_sha>`), case-insensitively.** Build junk (`__pycache__/`, `*.pyc`, `.pytest_cache/`, `.mypy_cache/`, `.ruff_cache/`, `node_modules/`, `.DS_Store`, `*.egg-info/`) is unstaged with `git reset <main_sha> --pathspec-from-file` (literal pathspecs, a NUL-separated file, so any number of paths fits). The files stay on disk in the worktree, and the run log gets a `log` event listing up to 100 of them. Likely secrets block the ticket with no retry: `refusing to commit likely secrets: <files>`. So does any added or changed file over 5 MB, where MB is 1,048,576 bytes: `file too large to commit: <file> (12.3 MB)`.
187. **The integration journal is schema version 3, not 2.** T13 already shipped version 2 (`progress_note`, `reset_at`). The `integrations` table has the planned columns. `state` adds `abandoned` to `merging | committed | advanced | tagged | done`: an integration that stops before main moves (a conflict, failing gates, a block, a wait) is closed as `abandoned`, so startup recovery doesn't put a blocked or retrying run back to `awaiting_approval`. Each state is committed in its own transaction before the next step starts (WAL, `synchronous=NORMAL`, which survives a process crash, see 59).
188. **Startup recovery of the journal runs after the run log's recovery and before T08's worktree recovery.** Main at the squash commit, or past it (`merge-base --is-ancestor`, in case the user committed on top before the restart): finish idempotently with the tag, ticket and run `done`, teardown and the `integrate` event. Otherwise, with a clean main checkout: put the worktree back on its branch and set ticket and run to `awaiting_approval` with `integration interrupted; run spool run integrate <project> <ticket>`. With a dirty checkout: touch nothing, with reason `integration interrupted while updating <repo>; check git status there before retrying`. A main checkout mid-rebase or mid-merge is reported and skipped, and its row stays open. An `interrupted` run is reopened (`reopen_run`) before its status is set. A recovered row is closed, so a second recovery changes nothing.
189. **The integrator closes the run itself.** `finish()` (tag, ticket `done`, teardown, run `done`, event, journal `done`) is shared by `LocalIntegrator` and recovery, so a crash at any point after the advance ends the same way. The loop's `done` handling skips a run that is already `done`. The teardown is given the branch name explicitly, because a detached worktree doesn't tell git which branch it belongs to.
190. **`spool run integrate <project> <ticket>`** (`POST /api/projects/{name}/tickets/{id}/integrate`) continues the ticket's latest run if both are `awaiting_approval` and the worktree exists. It is `RunLoop.integrate_ticket`, not a function in `integration.py`, because it needs the loop's per-project lock and worker thread; it shares `_continue` with `resume`. It always uses the real integrator, even with `run.integration: hold`, since that is how a held ticket is merged. The ticket goes back to `running` while it integrates.
191. **Hold mode is `run.integration: hold` in `project.yaml`** (default `local`). The daemon's `RunLoop` uses `LocalIntegrator`; a project in hold mode gets `HoldForIntegration` per run, whose message now names the command: `T04 approved; merge it with \`spool run integrate demo T04\` — worktree kept at <path>`.
192. **T10's retry note is split into `user_note` and `system_note`**, rendered under "Note from SpoolHQ" (first) and "Note from the user". SpoolHQ's own explanations (an early stop of either agent, a conflict) go in `system_note`, without the old `SpoolHQ:` prefix, so "Note from the user" appears only when a user wrote one. No golden snapshot had a note, so none changed.
193. **The event kind is `integrate`** (`{"commit", "tag"}`), named as the ticket names it, not dotted like the run and attempt kinds.
194. **A git error mid-squash restores the worktree.** If anything fails before main has moved, the worktree goes back on its branch and the journal row is closed before the error reaches the loop, which blocks the run with `internal error: …`.
195. **The implementer may not run the project's `install` command** (amends 89). In M1 the agent ran `just install` inside its sandbox, where pnpm couldn't use its global store and created `.pnpm-store/` in the worktree, which was committed with a symlink in it. Installs belong to the gates, outside the sandbox (91). `Commands.for_implementer()` (all commands but `install`) feeds both the implementer's policy and its prompt, so the prompt doesn't list a command the agent would be denied. `spool prompt show` uses it too. The reviewer's policy is unchanged.
196. **The diff guard also drops `.pnpm-store/`, `.npm/` and `.yarn/cache/`** (extends 186). `.yarn/cache/` is matched as a two-folder path anywhere in the tree, so `.yarn/releases/` is still committed.
197. **An added or changed symlink whose target is absolute (POSIX or Windows) or leaves the repo blocks the ticket**: `refusing to commit a symlink that points outside the repo: <path> -> <target>`. Modes and targets come from the index (`git diff --cached --raw`, then `git cat-file blob`), not the disk, because Windows checkouts often store symlinks as plain files. Targets are resolved lexically from the link's folder. Junk is dropped first, so the M1 link `.pnpm-store/v11/projects/<hash> -> ../../../desktop`, which points inside the repo anyway, is left out rather than blocking. Symlinks within the repo stay allowed.
198. **The reviewer judges only the committed diff.** A new rule says the empty placeholder files the sandbox creates at the root (`.env*`, `package.json`, lockfiles, `.npmrc`, see 104) are not part of the change. In M1 the reviewer listed them among its reasons for `needs_human`. The reviewer prompt now has a golden snapshot (`tests/fixtures/review/expected/reviewer_prompt.md`, rewritten with `SPOOLHQ_UPDATE_SNAPSHOTS=1`).
199. **SpoolHQ's own `.gitignore` ignores `.pnpm-store/`.**
200. **`spool run status` takes the last merged ticket from the integration journal**: the newest `done` row (by `updated_at`, then id; `last_integration`), its `commit_sha` and the tag `ticket/<id>` (`tag_name`, as `finish` creates it). The journal is one indexed query and holds exactly the merged commits, whereas the `integrate` events would need a scan across runs. `runs/current` returns it as `last_merged` (the full sha). The CLI keeps the line `no active run in '<project>'` and adds `last merged: T04 · 1a2b3c4 · ticket/T04` under it. The short sha is cut to 7 characters in the CLI rather than asking git (`rev-parse --short`), since the CLI has no repo access and the line is only for reading.
201. **Agents started by SpoolHQ don't edit `PROGRESS.md`.** In M1 the T29 agent followed `CLAUDE.md` and wrote its own entry, and integration appended SpoolHQ's, so the merge had two. The implementer prompt now says to leave the file alone and end with the `<progress>` block; `CLAUDE.md` keeps the rule for manual sessions and says the same for SpoolHQ's agents. The diff guard doesn't enforce it: a ticket may legitimately need to fix the file.
202. **The per-ticket token budget counts weighted tokens**: input + output + cache writes + cache reads × 0.1 (`core/tokens.py`, floor division). Cache reads cost a tenth of fresh input, and every turn re-reads the whole context, so raw counting made a 1M budget last about 20 turns. T29's implementer made 34 calls for about 2.2M raw tokens, 2.1M of them cache reads: about 300k weighted. The run log keeps the raw numbers and adds `attempts.cache_read_tokens` (schema version 4); `spool runs list` and `spool runs show` print the weighted total next to them. `spool run status` still shows raw tokens.
203. **The implementer prompt asks for fewer, larger turns**: one Edit or Write per file where it can, independent reads and searches in the same turn, and the full lint and tests only when it thinks it is done (and after fixing a failure). Each turn re-sends the whole context, so the number of turns drives the cost.
204. **The prompt takes only the newest history**: `context.progress_entries` (default 3) `PROGRESS.md` entries plus its preamble, and `context.decisions_lines` (default 20) non-blank `DECISIONS.md` lines, then the character budget as before. Lines rather than entries for `DECISIONS.md`, because its entries are numbered lines, not `## ` sections. One line after the blocks points the agent to the files for older entries. It is shown whenever either block is present, not only when something was cut, so the template needs no extra variable.
205. **`npm_config_verify_deps_before_run=false` is in `ENV_SET`.** pnpm otherwise tries to install from the network before each `pnpm run`, which fails in the sandbox and adds noise; the gates' install provides the deps. `ENV_SET` goes to every `claude` process, so the reviewer gets it too; it can't run commands, so that changes nothing for it.
206. **The planner is read-only** (T15): `AgentPolicy.read_only_for` (Read, Glob, Grep, the reviewer's deny list) with the project's repository as working folder, so it can look at existing code; nothing is written, so no worktree. Role `agents.planner`, falling back to `agents.default` (only `claude-code-cli` exists). 30 turns.
207. **Planner inputs:** `CONTEXT.md` and an optional template description (`--template-description FILE`, `None` until T16), both untrusted; the tickets that must be kept, with their bodies; the planning rules in `prompts/planner.md.j2` (package `services/context/prompts/`), overridable in `<workspace>/prompts/` like T10's. Untrusted text is only a variable, escaped for its own `<spec>`, `<template>` or `<kept_tickets>` block.
208. **Planning rules:** tickets of 1.5–4 h with a one-line purpose, scope bullets and a testable "Done when"; one ticket = one branch = one merge, tests in every ticket; the last "Done when" item is `` `<test command>` passes `` with `commands.test`; `review_required: true` for migrations, auth, CI, security-sensitive or destructive work; an applied template's setup counts as done.
209. **The planner ends with one `<plan>` JSON block, validated in code:** strict Pydantic (unknown keys refused), ids `T\d{2,3}`, unique, not a kept ticket's; `estimate_h` 1.5–4; non-empty `scope` and `done_when`; titles cleaned to one line without control or format characters and cut to 80; the combined graph (kept + new) passes T06's `validate_plan`. Invalid output is retried once with the exact errors (the prompt's "Your previous answer was invalid" section, as T12 does; the planner has no `system_note`, which is the implementer's), then fails with `planner output invalid: <errors>` and writes nothing.
210. **"New ids continue from the highest existing number" means:** a new id must be either the id of a draft the plan replaces or above every existing ticket's id. The prompt names both (`reusable`, `next_id`). Without the reuse, a re-plan could never keep T01–T18's ids after one draft was edited.
211. **Missing test-command item is appended, not refused.** If a ticket's last "Done when" item isn't exactly `` `<test command>` passes ``, code adds it. Retrying a whole plan for one missing line costs more than it is worth, and the result is the same.
212. **Draft files:** `<id>-<slug>.md` (the branch slug, `slugify` moved to `core/ids.py` so `services/planner` needn't import `services/git`), status `draft`, frontmatter dumped with the project's ruamel setup (so odd titles are quoted correctly), body `## Purpose`, `## Scope`, `## Done when` (checkboxes); they round-trip through T05.
213. **Edit detection by hash:** `<workspace>/.spoolhq/plan.json` (`{"generated_at", "tickets": {"T01": "<sha256>"}}`) records each draft written. On re-plan a draft with its recorded hash is replaced (deleted if the new plan drops it); an edited draft (hash differs) or a hand-made one (no hash) is kept byte for byte and given to the planner as fixed input; a ticket not in `draft` is never touched. A kept ticket that depends on a dropped draft fails with `T18 is kept and depends on T17, which the new plan drops` (retried like any invalid output). A missing or unreadable `plan.json` keeps every draft.
214. **All-or-nothing writes:** every new file and `plan.json` is staged as a hidden temp file beside its target, the files being replaced or deleted are moved aside, the temps renamed in; any error restores the old files. Approval writes the same way.
215. **Invalid ticket files stop the planner** before it starts (`fix them first (spool plan check)`), since it can't tell what to keep.
216. **`spool plan generate|show|approve` run locally** (like `spool review`), in the existing `cli/plan.py`. `approve` checks the whole graph (invalid files and T06 problems, all named), then moves every draft to `ready` through `check_transition`, writing only the status lines. No drafts: `nothing to approve`, exit 1 (and 409 from the API), so "approve twice" is visibly a no-op.
217. **Plan runs in the run log:** `runs.kind` (`ticket` | `plan`, schema version 5). A plan run's ticket id is `plan`, its one attempt has kind `plan`, its folder is `runs/plan/<NNN>/`, and its usage is recorded like any attempt's, so `spool runs show` gives the weighted total. The run ends `done`, `blocked` with the error, or `cancelled`. The run loop's resume skips plan runs.
218. **The API runs the planner in `PlanJobs`** (`services/runloop/planning.py`): checks needing no agent (project, `CONTEXT.md`, ticket files) answer at once (404/409); then a worker thread runs `generate_plan` and `POST /api/projects/{name}/plan` returns 202 with the run id. One plan per project at a time (409); it doesn't wait for or block a ticket run, since it touches only drafts. `Agents.planner` (default: the implementer's runner) supplies the runner. It lives in `runloop` because only that package may import both the planner and the run log.
219. **The planner's budget is `agents.budget_per_ticket.tokens` over both attempts together**: one plan counts as one ticket. The attempt gets the tokens left as `max_tokens`; with none left there is no retry (`budget used up: …`).
220. **The dashboard plan fixture uses 1.5 h for T01 and T02** (1 h in T05's fixture), because the planner's rules refuse estimates under 1.5 h; ids, titles, dependencies and the other estimates match T05's fixtures. T01 (CI) and T04 (migrations) are `review_required: true`, as the rules say.
221. **Copier is the template engine** (T16): `copier==9.19.1`, the current release (2026-10-13), MIT licence. It is the one new dependency; it brings dunamai, funcy, jinja2-ansible-filters, platformdirs, plumbum, prompt-toolkit, pyyaml, questionary and wcwidth with it. Only its public API is used (`copier.run_copy`, `copier.Settings`, `copier.errors.UnsafeTemplateError`); `Worker` is deprecated as internal in 9.x.
222. **Templates get no trust.** SpoolHQ never passes `unsafe=True`/`--trust`, and passes `settings=copier.Settings()` (empty): Copier's `Worker` otherwise loads the user's settings file, whose `trust` list skips the unsafe check and whose `defaults` change answers. Before Copier starts, every YAML document of `copier.yml`/`copier.yaml` is checked for `_tasks`, `_migrations` and `_jinja_extensions`; Copier's own check (tasks and extensions, also when pulled in with `!include`) is mapped to the same message, `template '<name>' needs Copier tasks or extensions, which SpoolHQ doesn't run`. Copier 9.19.1 renders with its `SandboxedEnvironment` (a `jinja2.sandbox.SandboxedEnvironment` subclass that also blocks `PurePath.parser`, Pydantic's `parse_file`/`parse_raw` and its settings loader), its loader refuses includes outside the template root, and it refuses symlinks pointing outside the template unless `_preserve_symlinks` is set (then they are copied as links, not followed).
223. **The contract is `spoolhq-template.yaml`** at the template root: `name` (slug), `description` (non-empty, at most 2,000 characters), `commands.install|lint|test` (required, T11's no-shell rule) and optional `commands.dev`. Errors are one line each, `template '<label>': spoolhq-template.yaml: <path>: <message>`; a missing gate command reads `… has no 'test' command; every template must declare install, lint and test`. `dev` is documentation only: `project.yaml`'s `commands` model forbids extra keys and no gate runs it. SpoolHQ also passes the file to Copier's `exclude`, so a template that forgets `_exclude` doesn't leak it.
224. **Sources:** a git URL is anything with a scheme, `user@host:`, `gh:`/`gl:`, or ending in `.git` (so a local bare repo works); then anything with `/`, `\`, a leading `.` or `~` is a local folder; anything else is a built-in name. Built-ins are package data in `daemon/src/spoolhq/templates/<name>/` (the root `templates/` README now points there). A git URL is cloned once with SpoolHQ's `run_git` (hooks disabled) to resolve `--template-ref` to a commit and read the contract; the source and commit are printed before generating, and Copier renders that exact commit (`vcs_ref=<sha>`). Without `--template-ref` it is the default branch's head, not Copier's "latest tag", so what is printed is what is rendered. A local folder that is a git work tree records its `HEAD` (Copier renders `HEAD` plus uncommitted changes). Refs starting with `-` are refused.
225. **`spool init --template` refuses anything but a missing or empty `--repo`**, checks the workspace name first, generates with the template's defaults and `project_name`, then `git init --initial-branch=<--branch>` and commits `chore: apply template <name>` through T08's `commit` helper (hooks and signing off, `user.useConfigOnly`: the user's identity is required and nothing is written to any git config). 230. **`fastapi-react` structure choices:** the backend is a uv virtual project (`package = false`) and the package names are fixed (`backend`, `frontend`), so the committed `uv.lock` and `pnpm-lock.yaml` don't depend on the project name and only `README.md`, `CLAUDE.md` and the answers file are rendered (`_templates_suffix: .jinja`). Plain `fetch` through `shared/api`, no TanStack Query, to keep the example small. import-linter layers `app.main` → `app.api` → `app.services` → `app.core`, plus "services never import FastAPI or Starlette" and "core imports nothing above it"; no per-domain independence contract while there is one domain. `.env` is read from the repository root (`.env.example` committed).
231. **The built-in template is excluded from SpoolHQ's ruff and mypy** (`extend-exclude`, `exclude`): it has its own lint setup and its imports (`app.…`) don't resolve inside the daemon. Its files still count toward SpoolHQ's 500-line check. Its real check, `tests/services/templates/test_fastapi_react.py` (`integration`), generates it, runs `spool init --template` and `spool templates check fastapi-react`, and plants a FastAPI import in `services/` and a sibling-slice import in `features/` to see `just lint` fail; it is skipped only where `just`, `uv` or `pnpm` is missing.
232. **`fastapi-react`'s justfile exports `PYTHONUTF8=1`.** Under the gates' environment on Windows, Python's piped stdout is cp1252, and import-linter's progress output (rich, with emoji) crashed `lint-imports` with `UnicodeEncodeError`. Setting it in the justfile fixes the generated project for every caller (gates, CI, a user piping output) without changing SpoolHQ's gate environment.
233. **SpoolHQ clones git-URL templates and hands Copier a plain folder (supersedes the clone part of 221–231).** Copier's own `git clone`/`checkout` runs with the user's global git config, so a global `core.hooksPath` would run its hooks. SpoolHQ clones through `run_git` (hooks and signing disabled), checks out the resolved commit, removes `.git` and passes the folder, so Copier never runs git. Copier then records the temp folder, so SpoolHQ writes the git URL and commit back into the answers file (`_src_path`, `_commit`) for a later `copier update`. A local folder that is a git work tree still goes through Copier's own clone (out of T17's scope; noted for a follow-up).
234. **The `fastapi-react` template uses `httpx` 0.28.1 again, not `httpx2` (supersedes the `httpx2` pin in 229).** `httpx2` is published by Pydantic Services Inc. from `github.com/pydantic/httpx2` as a "continuation" of HTTPX under Pydantic's stewardship; Starlette 1.8 prefers it and names it in its changelog and docs (encode/starlette #3291, #3323), but nothing from the HTTPX maintainers (encode/httpx is not archived and its README doesn't mention it) makes it their official successor. Starlette's `TestClient` still works with `httpx` and only warns (`StarletteDeprecationWarning`), which the template accepts.
235. **GitHub delivery is chosen per project and per ticket (T17).** A project with `git.remote` delivers to GitHub, one without it keeps T14's local merge. `delivery_mode(ticket, attempt)` is the one place that picks `direct` or `pr` (`review_required` → `pr`), so T18 only extends it. `Delivery` subclasses `LocalIntegrator` and overrides two hooks, `_prepare` (fetch first) and `_deliver` (push instead of a local fast-forward), so the merge, gates, diff guard and squash stay one code path.
236. **Git auth is the user's own git setup; SpoolHQ fetches by URL.** Fetch and push go through `run_git` with the user's credential helper or SSH agent; SpoolHQ never writes credentials anywhere and hooks stay disabled. `git.remote` doesn't have to be a configured `git remote`: SpoolHQ fetches the URL into `refs/spoolhq/remote/<branch>`, outside `refs/remotes/`, so the user's remotes and `origin/main` never change. Tests point the GitHub URL at a local bare repository with `url.<bare>.insteadOf` in the test repository's config, so production code has no test hook.
237. **Push before local main moves.** In direct mode the squash commit (on top of the fetched remote main) is pushed first, plainly (never `--force`); only then is local `main` fast-forwarded. A push refused as `fetch first`/`non-fast-forward` redoes the integration (T14's 3 tries); any other refusal blocks with git's error. If local `main` can't be fast-forwarded after the push (it moved, or the checkout got dirty), it is left alone and the ticket is done: the next fetch catches it up. A failed tag push is logged, not blocking. Before pushing, the commit's parent is checked against the fetched remote ref, so the user's own unpushed commits can never ride along.
238. **A failed fetch blocks; recovery that can't fetch waits.** During integration a failed fetch blocks the ticket with git's error (as any other push failure does). At startup, an open journal row whose remote can't be fetched is left open and reported, like a row whose main checkout has a rebase in progress, because finishing or undoing it would be a guess.
239. **The GitHub token: environment, then the OS keychain (T17).** `SPOOLHQ_GITHUB_TOKEN` wins; otherwise `keyring` (25.7.0, MIT, pinned), service `spoolhq`, key `github`. `spool secrets set github` reads it with `getpass`, never from argv. It goes only into the `Authorization` header; `GitHubClient.redact` replaces it in every error, httpx exceptions are not chained (they hold the request), and the daemon log redacts it as it does the daemon token. Only the API needs it: direct mode works without one, and PR mode without one blocks before anything is pushed. Tests install an in-memory keyring backend (autouse) and point subprocesses at keyring's null backend, so no test touches the real keychain.
240. **Pull request text is escaped, not sanitised.** Ticket and agent text in the body is backslash-escaped for markdown and `& < > @` become HTML entities (`@` so nobody is mentioned); the title is the squash commit's subject (one line, 72 characters). The body (title, purpose or scope, the reviewer's verdict per "Done when" item, a gate table, the run id) is cut on a line boundary at 60,000 characters, under GitHub's 65,536 limit.
241. **The run stores its pull request's number, URL and branch (schema 6).** The branch is stored rather than derived from the title (which can be edited while the PR is open) or read back from the API (untrusted). The journal row of a delivered PR moves to a new state, `pr_open`, which recovery ignores; the poller sets it `done` with the merge commit (so "last merged" shows it) or `abandoned`.
242. **Changes requested continue the same run.** The poller recreates the worktree with `WorktreeManager.create` and `reset --hard` to the fetched PR head (no change to `worktrees.py`), records the review's text and id in a `log` event and starts a `pr_changes` attempt through the run loop; `previous_attempt` reads the newest such event into the prompt's new `pr_review` field. The approved commits are pushed on top of the PR branch as they are: no new squash and no merge of main, so the push is a fast-forward. A review counts once (its id) and only if it is newer than the last attempt.
243. **Polling runs in the daemon process, and in its own module.** `GitHubPoller` (`services/runloop/polling.py`) runs on a daemon thread every 60 s and on demand through `POST /api/projects/{name}/github/sync`. It acts on runs under the run loop's lock with the loop's own helpers (`_project`, `_check_free`, `_manager`, `_continue`) instead of new public methods, because `loop.py` is at the 500-line limit; for the same reason PR text lives in `pr_body.py`. A rate limit stops all calls until GitHub's reset time; any API error is logged and retried at the next poll.
244. **What a merged PR does to local main.** The merge commit is tagged (and the tag pushed) once it is on the remote's main. Local main is fast-forwarded when it is behind; a dirty checkout waits for the next poll; a local main with its own commits is left alone (the ticket is still done), and the next integration's fetch-first rule blocks on those commits.
245. **Failures around a pull request.** Opening a PR that GitHub refuses deletes the pushed branch again and blocks. A PR branch that already exists with other commits, or moved on GitHub during a `pr_changes` attempt, blocks: SpoolHQ never force-pushes. `spool run integrate` refuses a ticket waiting on a PR. There is no ticket API yet (T19), so the PR shows in `spool tickets show` (from the run log, read-only) and in the run views.
246. **A local template folder that is a git repository is cloned like a git URL (T18 step 0; closes the follow-up in 233).** Anything with a `.git` entry (folder or file) goes through the same `run_git` clone (hooks and signing off) into a temp folder at `--template-ref` (default `HEAD`), and Copier gets the plain folder. Uncommitted changes in the template folder are therefore no longer rendered: what is recorded (`template.ref`, the answers file's `_commit`) is exactly what is rendered. `--template-ref` now also works for such a folder. `ResolvedTemplate.vcs_ref` is gone, since Copier never renders a git work tree any more.
247. **Remote git calls run ssh in batch mode.** `run_git(..., remote=True)` (fetch, push, remote branch delete, template clones) sets `GIT_SSH_COMMAND=ssh -o BatchMode=yes`, so a passphrase-protected key with no agent fails at once. A user's own `GIT_SSH_COMMAND`, `GIT_SSH` (which `GIT_SSH_COMMAND` would override) or `core.sshCommand` (read with `git config --get` in the call's folder) is kept, and one warning per daemon process says a passphrase prompt could hang until the timeout.
248. **The merge policy is pure and records every hit (T18).** `services/runloop/policy.py` takes plain values (the ticket flag, the squash diff's `ChangedFile`s, the settings, the reviewer's summary, hold mode) and returns `PolicyDecision(needs_human, rules)` with every `RuleHit`. `delivery_mode(decision, has_remote)` maps it to `direct`, `pr` or `approval`; it moved from `delivery.py` to `policy.py`, because `integration.py` needs it and `delivery.py` imports `integration.py`. Rule order in the record: `needs_human` first (so the reviewer's summary is what a person reads first, in the run reason and the PR body), then `review_required`, `diff_size`, `protected_paths`, `hold_mode`.
249. **The policy runs on the staged squash, before the commit and before the `PROGRESS.md` entry.** That is after T14's merge-in of main, the gates rerun and the diff guard, so it sees what would land, minus SpoolHQ's own progress entry (a 400-line agent change stays at 400 lines). Diff statistics come from one `git diff --cached --numstat -z --find-renames` call, which names both sides of a rename, deletions and binaries (`-`); `--name-status` would add nothing, so it isn't run. Lockfiles are recognised by file name in any folder. Without a remote, `approval` undoes the squash (worktree back on its branch, journal `abandoned`) and returns `held`: no commit exists until a person approves.
250. **A `needs_human` verdict is integrated like an approval and the policy sends it to a person.** The attempt keeps status `needs_human`; `next_kind` treats it like `approved` (only integration is left), so a resumed run doesn't start over. The run loop has no other path to the policy: the reviewer runs only after passing gates, and every blocking outcome (retries used up, agent errors, the reviewer changing the worktree, diff-guard refusals) still ends the run before integration.
251. **Hold mode is a policy rule (`hold_mode`), not a separate integrator.** The run loop no longer picks `HoldForIntegration` for `run.integration: hold`; `Delivery` merges and squashes as usual and the policy holds every ticket, listing any other hits too. `hold_mode` always means local approval, even with a remote, as before T18. `HoldForIntegration` stays only as a test seam.
252. **Approval is recorded per attempt, in the run log.** `spool run approve` on a run whose latest decision was `approval` appends a `log` event `{"approved_attempt": <attempt id>}`; the next decision for that same attempt drops `hold_mode`, turns `approval` into `direct` and records `"approved_by_user": true`. Any new attempt (a gate retry after main moved, a conflict retry, a reject) needs a new approval. Keeping it in the run log rather than in memory means an approval survives a daemon restart in the middle of the integration. A ticket waiting for another reason (dirty main checkout, interrupted integration) is not marked approved, so `spool run integrate` there doesn't skip the policy. With a remote in hold mode, an approved ticket that still hits other rules opens a pull request, as `spool run integrate` did before.
253. **Reject reuses `pr_changes`.** `spool run reject --note` logs `{"user_note": note}` and continues the run with a `pr_changes` attempt; `previous_attempt` reads the newest `pr_review` or `user_note` event into the prompt (the existing "Note from the user" section). An empty note is refused in the CLI and the service (409 from the API).
254. **The run row stores the latest decision as JSON (`runs.policy`, schema 7), written with its `policy.decision` event in one transaction** (`services/runs/policy.py`). The API's run view adds `policy` (`mode`, `rules`, `summary`). `spool runs show` prints `policy: <mode> · <summary>` and `spool run status` the `needs you: …` line.
255. **`merge_policy` settings follow the ticket, not T04's placeholder.** `max_direct_diff_lines` is renamed `max_diff_lines` (10–100,000) and `always_pr` is removed: it was never wired, and `review_required` or hold mode cover it. A `project.yaml` that still has either key is refused by the strict model (pre-alpha, no migration). `task.md`'s example now uses `max_diff_lines` too. Patterns: absolute (`/`, `\`, `C:`), a `..` folder (not any `..` substring, so `a..b.py` is allowed) or empty are refused. The matcher is a small regex translation (`*`, `?`, `**`), case-sensitive on every OS.
256. **PR-mode token check moved after the squash.** `Delivery._prepare` no longer knows the mode (the policy needs the squash diff), so a missing token now blocks in `_open_pr`, still before anything is pushed. `spool run approve` (alias `integrate`) and `POST …/approve` (alias `…/integrate`) replace `RunLoop.integrate_ticket`; `RunLoop.approve`/`reject` delegate to `approval.py` because `loop.py` is near the 500-line limit.
