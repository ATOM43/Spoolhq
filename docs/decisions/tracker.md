# Decisions · Tracker

Tracker sync (ClickUp). Listed in [DECISIONS.md](../../DECISIONS.md).

432. **Sync finds changes by comparing tickets and runs with what it last queued, not by hooks in each writer** (T24). Tickets change through the API, the CLI, the run loop and hand edits; hooking every writer would miss some (a CLI or editor change while the daemon runs) and couple the run loop to the tracker. Instead the sync thread lists the tickets every 5 s and compares each one's fingerprint (SHA-256 of title and body; `tracker_ref` and status left out) and status with `tracker_tickets`, and reads the newest 200 ticket runs for finished runs and pull requests. So the run loop has no tracker code at all, which is what makes "a tracker outage never changes a run's outcome" true by construction. The cost is a 5 s delay and a ticket listing per tick, which is small next to a run. When a tracker block first appears every ticket is pushed (the point of configuring one); runs that ended before that (`tracker_sync.baseline_run_id`) get no comment, so turning sync on doesn't post a comment per old run.
433. **The outbox is three tables in state.db (schema 9); only run comments and PR links are keyed** (T24). `tracker_outbox` holds the actions (`push`, `status`, `comment`, `link_pr`) with their failures and next try; `tracker_tickets` what was last queued per ticket; `tracker_sync` one row with the baseline run, the last error and the last success. In `state.db` rather than a new file because it is per project, shares the run log's WAL and lock, and the events it records go in the same database (SQL in `services/runs/outbox.py`, like `pulls.py`). `push` and `status` aren't keyed: at most one of each waits per ticket, a waiting push covers a status change, and the action reads the ticket when it is sent, so coalescing needs no payload. `comment:<run id>` and `link_pr:<run id>` are `UNIQUE` keys never deleted, so each is queued once across restarts. Done and failed rows are kept; they are small and show what happened.
434. **One sync thread serves every project and starts once a project has a tracker block** (T24). Like the GitHub poller: one daemon thread, projects in turn, one action at a time per project (a lock held while sending, never by the status route, so `GET …/tracker` answers while ClickUp hangs). It starts at daemon start if any project has a `tracker` block, or at the first `POST …/tracker/push`; a block added to a file later needs a push or a restart, which docs/tracker.md says. A project without a block is never scanned, so nothing is queued for it and its state reads `off`. A slow tracker on one project delays the others' sync, not their runs.
435. **Crash recovery adopts a task by its name prefix; the list is read once per adapter** (T24). Before creating a task the ClickUp adapter reads the whole list (100 per page, closed tasks included, at most 100 pages) and adopts the first task named `T04 · …`. Reading it once per adapter instance and adding the tasks it creates keeps the first push of a 50-ticket plan from costing 50 list scans against a 100-calls-a-minute limit; the cache is right because only this adapter creates tasks for the project, and a crash starts a new adapter that reads the list again. The adapter is rebuilt when the tracker settings or the token change. The `tracker_ref` is written after the call under `edit_lock` and `tickets_lock` (now public in `services/scheduler`) through the ticket store; a run-loop status save racing it can drop the ref, and the next push adopts the task again, so no duplicate comes of it.
436. **A tracker.failed event goes on the ticket's latest run** (T24). Events need a run (`events.run_id` is `NOT NULL` since schema 1, and SQLite can't relax it in place). A run comment or PR link has its run; a push or status failure uses the ticket's latest run, so the event shows in that run's history. A ticket that never ran gets only the log line and the project's `failed` state with `last_error`, which is where `spool tracker status` and the API read it.
437. **A rate limit pauses the project's sync and isn't a failure** (T24). A 429 is ClickUp asking to wait, not an error: the action's next try and the project's `wait_until` are set to `X-RateLimit-Reset` (a Unix time; ClickUp's docs don't say seconds or milliseconds, so values above 10^12 are read as milliseconds), clamped to 1 s–1 h, 60 s without the header. The pause covers the whole project because the limit is per token. Everything else (5xx, 4xx, timeouts, a refused redirect, no token, a missing status, an invalid ticket file) counts toward the 5 failures; even configuration errors retry, so fixing `status_map` or storing the token lets the waiting actions go through without a push.
438. **The dry run is local and asks no tracker** (T24). `spool tracker push --dry-run` reads `project.yaml`, the tickets and `state.db` (read-only) in the CLI, without the daemon, and prints create or update (with the status the map gives), each run comment and each PR link not yet queued. It doesn't ask ClickUp, so "changes nothing in ClickUp" also means "sends no request", and a task the crash recovery would adopt shows as a create; the docs say so.
439. **ClickUp API v2 checked on 2026-11-21: `markdown_content`, `notify_all` required** (T24). From developer.clickup.com: create `POST /list/{id}/task` and update `PUT /task/{id}` take the description as `markdown_content` (the reference's example shows `markdown_description`, which is the field GET returns, not one the schema accepts); `POST /task/{id}/comment` requires `comment_text` and `notify_all` (sent as `false`); `GET /list/{id}` returns `statuses[].status`; `GET /list/{id}/task` pages 100 tasks from `page=0` with `last_page`, closed ones with `include_closed=true`. Personal tokens go in `Authorization` without `Bearer`. The adapter talks only to `https://api.clickup.com`, with `follow_redirects=False`, `trust_env=False` and a 10 s timeout, and checks every id against `[A-Za-z0-9_-]{1,64}` before putting it in a path, since `tracker_ref` comes from a ticket file.
440. **Run comments are built from the run log only** (T24). `run <id>: <status>`, the attempt count, tokens (plus USD when a cost was reported) and the pull request or the `integrate` event's commit. The run's `reason` is left out: some reasons quote agent or review text, and ticket text is untrusted. The comment is built when it is queued (the run has ended, so its data is final) and stored in the outbox row, so a restart sends the same text.
446. **Retry re-queues the failed actions with their failures reset; nothing failed is a no-op** (T51). `POST …/tracker/retry` sets every `failed` row back to `pending`, due now, with 0 failures, so each gets its 5 tries again, and clears `last_error` and `failed_at`. It keeps the queue's rules (433): a failed push or status update that a pending action already covers is dropped, and a pending status update a re-queued push covers goes. With nothing failed it changes nothing and answers 200 with `queued: 0`, so a second click or a stale card is harmless; without a `tracker` block it is 409, like push. It doesn't lift a rate-limit pause, which isn't a failure (437).
447. **The sync thread also starts on a settings save or a state read with a tracker block** (T51). Supersedes the part of 434 that needed a push or a restart. `PUT …/settings` with a `tracker` block calls `start_if_needed`, and so does `GET …/tracker` for a project with one, which covers a block added to the file by hand: the app reads that state for every project it shows, so the thread starts within 15 s without a file watcher. `start_if_needed` is a lock and a check once the thread runs, so calling it on every read costs nothing.
448. **When the sync failed is a column of `tracker_sync` (schema 10)** (T51). Home's card shows the failure's age, and nothing stored it: `last_synced_at` is the last success and the `tracker.failed` event needs a run. `failed_at` is set with `last_error` by the 5th failure and cleared with it by a success or a retry; a one-line `ALTER TABLE` migration, so older `state.db` files upgrade in place.
